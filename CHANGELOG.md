- Section 3 was keyed two ways at once and the two disagree. Its opening sentence asked for every distinct value "exactly once each", which keys the table by value; the multi-condition bullet said "the property appears once, carrying every value the source showed for it", which keys it by property. Each clause is right about the case it was written for - one property with two values across themes needs the property key, and nothing needed the value key until a value turned up in two roles.
- 1.11.0 hit that case in the README and resolved it in the cell rather than in the rule: `#FFFFFF` served as the card surface and the CTA label, and it went in as one row whose property column read "Card background, and the CTA label", with the status column explaining "one value in two roles, so one row". The run logged the rule as still silent. Resolving it the other way is what the table is for: a row is what a token names, so the row count follows the roles, and the key is the property throughout.
- So one value in two roles is two rows, one per role, each with its own proposed name, and the repeated value in the observed column is the evidence that they coincide on this screen. One row loses the thing the developer opened the spec for, which token to reach for at each place, and one name for both asserts that the system wants them tied - a claim about the design system, not a reading of the screen, which is the invention the spine bans. Whether they should resolve to one underlying value is an open question when no token set was supplied.
- Two rows holding one hex are not the near-duplicate drift a token audit flags, and the rule says so: they are identical by intent, where drift is two values a few steps apart in one role.
- The README example carries it - `surface` and `text-on-primary`, both `#FFFFFF`, the second naming the first and pointing at the open question - and section 4's default row already recorded that label as `#FFFFFF`, so the second row is read off evidence the spec had. Open question #7's count of proposed names moves from four to five and names the pair.
- Section 6's rule and the README paragraph behind it both argued from the single row, so both are restated: a row names a side and never a pair, and the two `#FFFFFF` rows are the sharpest case, since the screen crosses each with a different partner - the surface backs the dark body text, the label sits on the blue fill. `references/handoff-template.md` carries the same key, so the template, the rule and the example agree.
- Nothing about the contrast checks moved: three distinct colors still cross into six ordered combinations, the screen still shows two, and both ratios are unchanged at 14.68:1 and 5.17:1.

## [1.10.0] - 2026-10-19

- Section 6 asked for a contrast ratio on "every foreground/background text pairing that appears in the token map", checked against SC 1.4.3 and SC 1.4.11. Both criteria exempt an inactive component, and the section said nothing about it: SC 1.4.3 excepts text that is part of an inactive user interface component under Incidental, and SC 1.4.11 excepts inactive components in the same words. A disabled control has no ratio to fail, and the instruction sent one to be computed and judged anyway.
- This is not a rare collision, which is what made it worth the release. Section 4 enumerates `disabled` for every component in the inventory, so wherever the source shows that state its fill and label land in section 3's token map, and "every pairing in the token map" then walks them into section 6. The two sections were each correct and the handoff between them produced a check the standard does not ask for.
- The cost is a developer instruction that breaks the thing the spec just documented. A greyed label written up as a 2.1:1 failure gets fixed the obvious way, by darkening it until it passes, and what that removes is the one visual signal saying the control is unavailable. A false finding that is merely noise wastes a line; this one spends the spec's authority asking for a regression, and it arrives cited to a success criterion that exempts the pairing.
- The rule now sits under the contrast bullet in section 6. The row is written with its ratio computed and carries `exempt - inactive component (SC 1.4.3 Incidental, SC 1.4.11)` where a verdict would go. Keeping the row is deliberate: a pairing with no row in section 6 reads as one nobody checked, which is the same gap a missing section 4 row leaves, so the exemption has to be visible rather than silent.
- Three boundaries ship with it, because each one is a way the exemption could be over-read. It covers the inactive component's own text and visual information and nothing adjacent, so a helper line or an error message beside a disabled control is ordinary text and is checked. It is keyed to the state rather than the component, so the same button's default, hover and focus rows are checked as before. And it needs the control to be genuinely inoperable: a control styled muted while staying operable is active, so calling it exempt is an invention, and where the source does not settle which it is the answer is an `OPEN QUESTION` rather than an assumed exemption.
- No other rule moved. The eight canonical states, the three answers in section 4, the per-condition column splits, the contrast-once-per-theme rule and section 8's tagging test are untouched, and the README worked example needed no edit - it renders no section 6, and its disabled row is `OPEN QUESTION #4`, so the example never produced an exempt pairing to show. `references/handoff-template.md` carries the exempt row in its section 6 skeleton with the three boundaries stated, and the README how-it-works bullet on citing success criteria by number now says a criterion's exemptions are cited the same way.

The spine's ban on inventing what the source does not show is what this breaks: one item in this render is not a claim that the list cannot be empty, and reading the row off the render rather than off the artifact is the invention the README already calls "not a dismissal".
- The illustration is now a button with a fixed label, the reason the README already carries in both places it shows a closed `empty` row - the worked example's table and the "How do I document component states?" answer, which states the governing test as well, that the reason is read off the artifact and that a reason needing a fact the source never showed is an invention rather than a dismissal. All three surfaces now show the same one. The bullet also states the test the example was standing in for - the reason is a fact about the artifact rather than about this render of it - and names the other branch for a list, a results area or a cart however it was photographed, pointing at section 8's `empty` paragraph for the flow fact that settles it.
- No rule changed. Section 4's three answers, the eight canonical states, section 8's roster and its `empty` paragraph are untouched; the hover half of the pair was already correct and keeps its wording.

## [1.8.0] - 2026-10-07

- The blocking test added in 1.7.0 decides a tag by where a default comes from, and its roster was short by one state and off by one name. Section 4 enumerates eight canonical states - default, hover, focus, active, disabled, loading, empty, error. The test placed focus on a cited standard, disabled, loading and error on not building the state at all, and hover and "pressed" on neither. `empty` was never placed, and `pressed` is a name that appears nowhere in the eight.
- What that left with no legal answer: an unshown empty state on a component that holds content - a list, a results area, a cart, a notification panel - photographed with content in it and never without. 1.7.0 made `NON-BLOCKING` with no written-out default illegal, and the test offered that question no default source, so the only tag left was `BLOCKING`. The shape of the question says otherwise: whether the content can be absent is a flow fact, which is the same question disabled, loading and error ask, and those three are the non-blocking group.
- So the gap did not read as a gap. It read as a blocking count one higher than the screen earned, in the number the closing status line calls the real signal for whether a screen is ready to build - the same failure 1.7.0 fixed by making the tag readable off the line, reappearing through the row the test forgot to name.
- Why it stayed invisible: the README example's component is a button with a fixed label, so its Empty row is `not applicable` and the one artifact anyone copies never reaches the question.
- Section 8 now carries the full roster under section 4's own names, and says it is complete on purpose: hover and active have no statable default, focus has the standard, and disabled, loading, empty and error are the four whose question is whether the state exists. Default is observed or there is no row to write. A state missing from the list would reach section 8 with no test to decide it.
- `empty` gets the one clause that separates it from the other three: it is the state the artifact itself most often answers, so a component that holds no variable content closes the row in section 4 with `not applicable` and never reaches section 8, and the question arrives only for a component that does hold content.
- `pressed` is retired for `active` in the rule, in the sorting sentence, and in the example's question #3, so the open question and the section 4 row it came from carry one name. `references/handoff-template.md`: the filling-in note maps all eight states onto the two default sources. README: the FAQ answer carries the four-state non-blocking group and says why a complete roster is what keeps the blocking count countable, and the paragraph under the example reads the Empty row as the other half of the test.

## [1.7.0] - 2026-10-01

- The README's worked example is the only full spec anyone copies, and its open-questions list tagged by feel. `NON-BLOCKING` is defined as "implementation can proceed with a stated reasonable default", and five of the seven questions carried the tag with no default stated anywhere in the line. Two of those five said the opposite in their own text: the pressed state "needs a fill or a transform before build", and the disabled question was "needed before a disabled style is specified", which is the `BLOCKING` definition word for word sitting under the other tag.
- What made it visible: the hover fill was `BLOCKING` and the pressed fill was `NON-BLOCKING`. Both are an unshown fill on the same button, neither is reachable from the one default-state image, and nothing in the spec said why they split. The status line's "1 blocking" rested on that, so the one number a reviewer reads to decide whether a screen is ready to build was a choice rather than a count.
- Section 8 now carries the test, and it is readable off the line rather than judged. A default is statable from exactly two places: a standard the spec already cites, or not building the thing at all. The focus ring takes the first, since section 6 cites WCAG 2.2 SC 2.4.7 and a visible indicator is required, so only the treatment is open. Disabled, loading, and error take the second, since the question is whether the state exists in the flow and nothing is built until that is answered. Hover and pressed have neither: the state exists whatever the build does, so there is nothing to leave out, and a fill derived from the default fill is the guess the spine bans.
- Two moves are named illegal. A `NON-BLOCKING` question with no default written out is tagged by feel, and a question whose own text says the answer is needed before the build is `BLOCKING` whatever tag it carries - the sentence and the tag cannot disagree.
- The example is rewritten to the test: #1 and #3 both `BLOCKING` and both saying no default is statable, the other five each writing their default out, and the status line at 2 blocking, which is now derivable from the list rather than chosen. The paragraph under the example says the two blocking entries are the two with no default, and says why sorting hover and pressed differently would be sorting by which row the writer reached first.

## [1.3.0] - 2026-08-19

- A spec covering two breakpoints had no legal token map. The output rules explicitly keep multiple breakpoints of one screen in one file, with a subsection per breakpoint under section 2, while section 3 kept a single "Observed value" column and required every property to appear "exactly once each". A card padding of 16px at 375 and 32px at 1440 therefore had no way to be recorded: two rows break the no-repeats rule, one row drops a measurement the source actually gave, and the only nearby rule - flag conflicting sources - misfiles an intentional responsive step as a discrepancy and sends the developer back with a question that has no answer.
- Generalized the per-theme handling added in 1.1.0 into one rule for declared conditions, theme and breakpoint alike: one column per condition in section 3, one row and one token name per property, a differing value is a variant and a one-condition value is a `NEW-TOKEN` for that condition.
- Defined a conflict, which was previously left to the reader: two sources claiming the same condition and disagreeing. A difference across a declared condition is not one, so the conflict rule no longer swallows responsive and theme variation.
- Section 1 records one named dimensions line per breakpoint. One line cannot describe two viewports, and picking one silently drops a measured value.
- `references/handoff-template.md` carries the same rule in all three places it appears, and the README adds an FAQ answer on covering mobile and desktop in one spec.
